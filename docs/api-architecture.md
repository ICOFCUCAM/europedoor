# §3 — The API, as it actually is

Written from the running system, not from a proposal. Everything below was
read out of the build, and `checks.py` asserts all of it on every run — the
contract, the terms, the key set, and the counts agreeing across documents.

The short answer to *"does EuropeDoor need the API architecture originally
proposed?"* is **no, not yet, and for a reason that is measurable rather than
stylistic**: there is no server, so there is nothing an API could do that a
static file does not already do faster and with fewer ways to fail.

---

## 3.1 The surface, in full

**Five JSON documents and one geometry file per country plus two continent levels. No server, no endpoint that can
return 500, no query parameter, no key, no rate limit.**

| endpoint | size | what it holds | who reads it |
|---|---:|---|---|
| `/api/atlas.json` | 303 KB | the planner index: every destination with interests, nights, cost band, season, coordinates, URL | **the site** — planner, Discover Mode, Travel DNA |
| `/api/search.json` | 461 KB | one flat searchable row per entity, with a pre-lowercased haystack | **the site** — search |
| `/api/graph.json` | 437 KB | every derived relationship edge, nine types | published only |
| `/api/countries.json` | 135 KB | country facts, regions, destinations, derived facts with sources, verification | published only |
| `/api/journeys.json` | 37 KB | every curated journey with its legs | published only |
| `/api/geo/*.json` | 1.9 MB | two continent levels of detail, one file per country, one derived-facts file | **the map**, on demand |

**Two classes, and the distinction is worth keeping.** Three of the five have
no in-page consumer at all: they exist because the data is public and the
documents are cheap. Two are load-bearing — if `atlas.json` changes shape, the
planner stops working, and only a check catches that. `checks.py` names the
key set each consumer reads and fails when one disappears.

## 3.2 Static, not dynamic — and what that removes

Every document is generated by `tools/build.py` and served as a file from a
CDN. That deletes most of what an API architecture is normally for:

| what a dynamic API needs | here |
|---|---|
| authentication | none — nothing is private |
| rate limiting | none — a CDN serves a file |
| pagination | none — the largest document is well under a megabyte |
| versioning | the build is the version; `generated: "build"` says so |
| error responses | there is no request that can fail server-side |
| a status page | if the CDN is up, the API is up |
| a schema registry | `tools/lib/data.py` validates the input; `checks.py` validates the output |

**`generated: "build"` is in every document on purpose.** It tells a consumer
the numbers were true when the site was built, not when they were fetched.
Nothing here is live and the documents say so rather than implying freshness
they do not have.

## 3.3 Derived, authored, or refused — per endpoint

| field | class | rule |
|---|---|---|
| `derived.iso3`, `derived.lat/lon`, `derived.population` | **derived** | from Natural Earth; each carries `source`; refused as authored keys in `data/` |
| region `position` | **derived** | the middle of the region's own destinations, with `positionSource` saying exactly that |
| destination `kind` | **mixed, and it says which** | `kindSource` is either the dataset or `editorial`. derived where a source exists, authored where none does |
| `population` on a destination | **derived, and often absent** | Natural Earth lists roughly half of them; the rest are absent, not estimated |
| graph `edges` | **derived** | from relations validated elsewhere; a stored edge table is refused by name |
| graph `km` | **derived** | the only weight in the system. `weight`, `score`, `relevance`, `confidence` are refused in any edge |
| `verification` | **derived** | confidence comes from source kind and age; an authored `confidence` is refused |
| journey cost | **derived** | the same arithmetic the planner uses, so a journey page and a plan cannot disagree |
| `rating`, `review_count`, `featured`, `price_from`, `opening_hours` | **refused** | checked in the *output* as well as the input, because a field can be absent from `data/` and computed into a document |

**One document filters and says so.** `/api/atlas.json` strips advisory
countries — Ukraine, Russia, Belarus — because it is a list of places to route
*through*, and routing somebody into one is the harm. `/api/countries.json`
keeps them, with the advisory attached, because it is a description of the
continent and a consumer deciding what to do about Belarus needs to be told
there is an advisory rather than handed a document in which it silently does
not exist. **Both behaviours are asserted**, and the check also requires
`atlas.json`'s own note to mention the stripping — a document that quietly
omits twelve destinations is worse than one that omits them and explains why.

## 3.4 Search: the request and response contract

**Request.** `GET /search?q=<sentence>`. That is the entire contract. There is
no search endpoint: the index is fetched once and every query runs in the
browser.

**Response** — `/api/search.json`:

    rows[]   k  kind ("City", "Place", "Country", "Region", …)
             n  name              s  sub-heading         u  URL
             t  pre-lowercased haystack   w  KIND weight, not a relevance score
             b  budget band       q  quiet flag          m  good months
             la lo  coordinates   ct kind of place       i  interests
             cs country slug
    counts   { countries, cities }   — read by the empty state, not typed into it
    interests, monthNames           — for reading the query back

**The interpretation is part of the response contract.** Every query is echoed
back as what the system understood, before results:

> *"romantic mountain villages near Milan"* →
> `near Milan: within 300 km` · `villages: destinations recorded as that` ·
> `reading that as: coast & beaches, islands, wine & drink, architecture, mountains`

That line exists because of a specific failure class. A search that silently
drops a word looks intelligent and is not, and the reader has no way to tell.
Two of the three search bugs found in this audit were only findable because
the interpretation is rendered — and the third was *caused* by it: a modifier
was displayed and then not applied, which is worse than not supporting it,
because it tells the reader it worked.

**`w` is a kind weight, not relevance.** A Country outranks a Place because a
country is a bigger answer, not because anybody scored the match.

## 3.5 The empty and error contracts

The part of an API design that usually goes unwritten, so it is written here.

| state | contract |
|---|---|
| **index loading** | *"Loading the index…"* — a real state, because a few hundred KB on a slow connection is a second |
| **index failed to load** | a warning note naming what did not load and what still works. `search.js`, `discover.js` and `my-europe.js` each have one; nothing falls back to an empty page pretending to be a result |
| **no results** | **names the constraint that emptied it.** Re-runs the query with each modifier dropped and reports what would come back: *"Dropping villages would leave 52 places, and dropping near Milan would leave 1."* — the numbers are computed live, not written here |
| **too short a query** | says what to try, rather than showing nothing |
| **planner cannot answer** | an explicit refusal: *"We could not build a journey we would stand behind"*, with the reason. It does not degrade silently into a worse itinerary |
| **a fetch inside the map fails** | the coarser map that is already drawn stays. A finer level of detail failing to load is not a reason to blank the continent |

**The rule underneath all six:** a failed request must never render as a
successful empty answer. That is the same rule as the third search bug, one
layer out.

## 3.6 Graph generation

`/api/graph.json` is built in one pass at the end of the build, from relations
that were validated when the data loaded. It is a projection, not a store.

    the nesting            → part_of, located_in
    §2.5 experience `at`   → available_at, carrying at/from/about
    journey legs           → includes, stops_at, with the day number
    story `places`         → about
    theme `stops`          → gathers
    event `city`           → happens_in
    §2.11 transport nodes  → serves, weighted in km
    haversine              → near, the same function the planner uses

**Nothing may write it.** `data/relationships.json` is refused by the
validator by name, and `checks.py` puts a floor under every relationship type
— because one relationship shipped at zero for one build when the derivation read the
wrong key, and a relationship that silently drops to zero is exactly what
nobody notices.

## 3.7 The client-side "API": saved state and Travel DNA

There is no user API because there are no users. What would be server state
lives in the browser, and the contract is a storage key rather than an
endpoint:

| key | holds |
|---|---|
| `europedoor.saved.v1` | destinations, places, **experiences**, journeys, themes, stories — six kinds |
| `europedoor.collections.v1` | user-made groupings of the above |
| `europedoor.dna.v1` | per-row adjustments to Travel DNA, marked `(adjusted)` |

**Saving is a DOM contract, not a JS call.** Any element with
`data-save="<kind>:<id>"`, `data-kind`, `data-label` and `data-url` becomes a
save button. That is why adding `saved_experiences` in §2.16 was a markup
change rather than a feature: the flow already existed and nothing had pointed
it at an experience.

**Travel DNA is derived, and states its own denominator.** It reads
`/api/atlas.json`, resolves the saved ids against it, tallies interests and
normalises. It says *"computed from the 5 places you have saved"*, says it is
not a personality test, recomputes on every page open, and has a floor of four
saved items below which it declines to say anything. A preferences form filled
in once describes who somebody was.

**Export is text.** No account, no sync, no server: the list copies out and
pastes in, with URL validation on import.

## 3.8 Geographic queries

There is no geographic API. There are three mechanisms and each is chosen by
where the answer is needed:

| question | answered | where |
|---|---|---|
| what is near this destination | precomputed | build time, into the page and `graph.json` |
| what is within 300 km of Milan | computed | in the browser, over `atlas.json` |
| what does this country look like | fetched | `/api/geo/country/<slug>.json`, on demand when a country is opened |
| what does Europe look like | inline | the coarse level of detail ships in `/map` so the map draws with JavaScript off |

**Measured, because §2.18 asked:** a 2 km radius over every place in the atlas ran in
**0.17 ms**, and every destination pair in **73 ms**, in pure Python. A
spatial index is an optimisation and there is nothing yet to optimise.

## 3.9 What should not be built yet, and the trigger for each

| not built | why | what would change it |
|---|---|---|
| a write API | there is no legal entity to be a data controller | incorporation |
| authentication | the saved-list feature works without it, with a better privacy story | a feature that genuinely needs identity across devices |
| pagination | the largest document is well under a megabyte | a document that stops fitting in a browser |
| an API key or rate limit | it is a file on a CDN | egress cost becoming material |
| a versioned API (`/v1/`) | there is exactly one consumer of the load-bearing documents, and it ships with them | a third party depending on a shape we then need to change |
| GraphQL or a query language | the whole graph fits in a browser; a consumer can hold it | a graph that stops fitting, i.e. the same trigger as Postgres |
| a search service | the index and a rule engine answer in the browser, offline | semantic search, which needs a model — Phase E |
| webhooks, live availability, booking | no inventory, no operators, no timetables | §2.8, which is gated on legal work |
| server-rendered personalisation | personalisation is derived in the browser from local state, and never leaves the device | the same trigger as authentication |

**The consistent reason across all nine: adding a server adds a thing that can
be down, be attacked, cost money and go stale, in exchange for capabilities
nothing currently needs.** Each row names what would flip it, so the decision
can be revisited on evidence rather than on appetite.

## 3.10 What is checked, so this document cannot quietly become false

`checks.py` → *"every published endpoint states what it is, and holds to its
contract"*, 72 assertions:

1. **Terms.** Every endpoint carries a `licence` with `use` and `attribution`,
   a `note` saying what it is, and `generated: "build"`. Two of the five
   shipped without any of that until this audit, and nothing noticed, because
   a missing key in a document nobody validates is invisible.
2. **Key sets.** Each consumer's keys are named; a renamed field fails the
   build rather than the browser.
3. **Counts agree** — with the dataset and with each other. `atlas.json`'s
   destination count must equal the atlas minus the advisory strip, and the
   note must say the strip happened. `search.json`'s counts must match the
   dataset, because the empty state prints them.
4. **Nothing invented.** `rating`, `review_count`, `featured`, `sponsored`,
   `price_from` and `opening_hours` are refused in the *output*, not only in
   the input.
5. **Every endpoint is documented** on `/api`.

Verified by breaking each one: removing a licence, truncating a document,
planting a `rating`.
