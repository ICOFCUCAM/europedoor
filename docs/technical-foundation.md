# EuropeDoor — Technical Foundation Package

The next artifact, as asked: the PostgreSQL/PostGIS model, the entity
relationships, the API, the Next.js structure, authentication and roles,
search, the AI architecture, and the seed-data structure.

**Read this first.** Everything below describes a stack this repository does
not run. Today EuropeDoor is 988 static HTML files generated by Python with
zero runtime dependencies, no database and no server. That is not an
oversight and it is not a prototype: it is why the site loads in one request,
costs nothing to host, cannot leak a database it does not have, and has 1,250
machine-checked assertions standing behind it.

So this package is a **destination with a trigger**, not a plan to start on
Monday. The trigger is at the end. Adopting it early buys a server, a bill
and an attack surface in exchange for features that are all blocked on the
same missing thing — an incorporated entity — and none of which the database
unblocks.

---

## 1. The data model

The core tables are already specified in `docs/product-specification.md`
§2.2, and this does not restate them. What follows is what that section does
not cover: the spatial layer, the layers the static build has no equivalent
for, and the constraints that carry the product's promises.

### 1.1 PostGIS

```sql
create extension if not exists postgis;
create extension if not exists pg_trgm;      -- fuzzy search, §6
create extension if not exists unaccent;     -- Malmö ↔ Malmo

-- Geometry lives on the destination, not on the region. A region is a
-- travel construct with no agreed boundary, and inventing a polygon for
-- "Fjord Norway" would be inventing data.
alter table destination
  add column geom geography(Point, 4326) not null;

create index destination_geom_gix on destination using gist (geom);

-- Nearest onward stops, which the static build computes at build time from
-- haversine. Same answer, same published rule.
create or replace function nearest_stops(dest_slug text, n int default 6)
returns table (slug text, name text, km numeric) language sql stable as $$
  select d.slug, d.name,
         round((st_distance(d.geom, o.geom) / 1000)::numeric, 0) as km
  from destination d, destination o
  where o.slug = dest_slug and d.slug <> o.slug
    and d.country_slug not in (select slug from country where advisory_level is not null)
  order by d.geom <-> o.geom
  limit n;
$$;
```

`<->` is the KNN operator and it uses the GiST index; `order by
st_distance(...)` does not, and will sequential-scan 319 rows today and
40,000 later. That is the one PostGIS mistake worth writing down in advance.

### 1.2 The tables the static build has no equivalent for

```sql
-- Identity. See §5.
create table account (
  id            uuid primary key default gen_random_uuid(),
  email         citext not null unique,
  email_verified_at timestamptz,
  display_name  text,
  locale        text not null default 'en',
  created_at    timestamptz not null default now(),
  deleted_at    timestamptz            -- soft, for the 30-day window in §5.4
);

-- Saved items. Today this is localStorage and a copy-paste transfer; the
-- shape is identical so a migration is an insert, not a redesign.
create table saved_item (
  account_id  uuid not null references account(id) on delete cascade,
  kind        text not null check (kind in
                ('city','place','journey','theme','story','itinerary')),
  ref         text not null,
  collection  text,
  saved_at    timestamptz not null default now(),
  primary key (account_id, kind, ref)
);

-- An itinerary is a document, not a row per stop: it must survive the
-- Atlas changing underneath it. A trip saved in March that silently
-- re-routes in June because a destination was re-tagged is a bug the
-- reader cannot see.
create table itinerary (
  id          uuid primary key default gen_random_uuid(),
  account_id  uuid references account(id) on delete cascade,
  title       text not null,
  inputs      jsonb not null,     -- exactly the planner's opts object
  route       jsonb not null,     -- the resolved stops, frozen
  engine_ver  text not null,      -- which scoring rules produced it
  created_at  timestamptz not null default now()
);

-- Provenance, per claim. The static build has this already
-- (data/countries/*.json > checked.sources); relational form:
create table fact_check (
  id          bigserial primary key,
  entity_kind text not null,
  entity_ref  text not null,
  claim       text not null,          -- "Currency and blocs"
  source_name text not null,
  source_kind text not null check (source_kind in
                ('official','operator','municipal','press','editorial')),
  source_url  text check (source_url like 'https://%'),
  checked_by  text not null,
  checked_on  date not null,
  -- Confidence is DERIVED, never stored. A column somebody can write to is
  -- a column somebody writes 'high' into.
  confidence  text generated always as (
                case when checked_on < current_date - interval '365 days' then 'low'
                     when source_kind = 'official' then 'high'
                     else 'medium' end) stored
);
create index fact_check_entity on fact_check (entity_kind, entity_ref);

-- Photographs. The register in data/images.json, relationally. Same rule:
-- not-null everywhere it matters.
create table image (
  key           text primary key,
  file          text not null,
  alt           text not null check (length(alt) >= 12),
  photographer  text not null,
  source_url    text not null check (source_url like 'https://%'),
  licence       text not null check (licence in
                  ('CC0','CC-BY-4.0','CC-BY-SA-4.0','Pexels','Unsplash',
                   'commissioned','licensed-stock','owner-supplied')),
  focal_x       smallint not null default 50 check (focal_x between 0 and 100),
  focal_y       smallint not null default 50 check (focal_y between 0 and 100)
);
```

### 1.3 The constraints that carry the promises

These are not hygiene. Each one is a promise the product makes in public,
written where it cannot be forgotten:

```sql
-- No place is purchasable. Sponsorship attaches to a provider and reaches
-- directory surfaces only. This is the schema-level version of the
-- editorial wall, and it is the only version worth making.
alter table destination add constraint destination_never_ranked
  check (true);   -- enforced by absence: there is no rank/boost/featured column
comment on table destination is
  'No rank, boost, featured or sponsored column. Ever. See docs/legal-position.md.';

-- Volatile fields are refused, not nullable. A null hours column invites
-- somebody to fill it in.
comment on table place is
  'No opening_hours, price or phone column: they move faster than we check
   them, and a wrong opening time sends somebody across a city.';

-- Advisory countries never reach the planner index.
create view planner_destination as
  select d.* from destination d
  join country c on c.slug = d.country_slug
  where c.advisory_level is null;
```

The strength is not the nodes. It is that `place → journey`, `place → story`
and `destination → theme` exist at all — most travel databases have the
hierarchy and nothing crossing it, which is why their "related" sections are
generated from tags and read like it.

## 3. API

`docs/product-specification.md` §2.3 has the endpoint list. What matters more
is the split, which is not where most projects put it:

**Public, static, no key** — already shipped, as four JSON documents built at
deploy time: `/api/atlas.json`, `/api/search.json`, `/api/countries.json`,
`/api/journeys.json`. These are read-only projections of committed data.
Keeping them static after the database arrives is deliberate: they are the
highest-traffic reads on the site, they change once per deploy, and putting
them behind a query is spending money to make them slower.

**Authenticated, dynamic** — everything that writes:

```
POST   /api/plan                    itinerary from inputs
GET    /api/me/saved                the saved list
PUT    /api/me/saved/:kind/:ref
DELETE /api/me/saved/:kind/:ref
POST   /api/me/itineraries          freeze an itinerary
POST   /api/providers/claim         claim a listing (evidence required)
GET    /api/providers/:slug/stats   the owner's own analytics
POST   /api/fund/interest           register interest — never money
```

**`POST /api/plan` must share one implementation with the browser.** The
scoring rules exist once, compiled to both. If the server ever disagrees with
`/plan`, one of them is wrong and nobody will be able to tell which. That is
the single most important line in this document.

Conventions: cursor pagination (never offset), `ETag` on every static
document, `Cache-Control: public, max-age=300, stale-while-revalidate=86400`,
RFC 9457 problem details for errors, and a version in the path only when a
breaking change actually happens.

## 4. Next.js structure

```
app/
  (marketing)/
    page.tsx                        the homepage
    manifesto/page.tsx
  europe/
    [country]/page.tsx
    [country]/[region]/page.tsx
    [country]/[region]/[destination]/page.tsx
    [country]/[region]/[destination]/place/[place]/page.tsx
  journeys/[slug]/page.tsx
  stories/[slug]/page.tsx
  experiences/[category]/page.tsx
  plan/page.tsx                     client, and the engine runs in the browser
  map/page.tsx
  my-europe/page.tsx
  api/…/route.ts
lib/
  engine/                           THE SCORING RULES, ONCE
    score.ts  plan.ts  cost.ts  parse.ts
  db/  schema.ts  queries.ts
  images/  picture.tsx  register.ts
components/
  atlas/  planner/  map/  trust/
content/                            the current data/ directory, unchanged
```

Three decisions inside that:

- **`lib/engine` is imported by both `app/plan/page.tsx` and
  `app/api/plan/route.ts`.** See §3.
- **Every Atlas page is statically generated** (`generateStaticParams` +
  ISR). They change when an editor commits, not when a reader arrives, and
  the current build proves 988 of them can be static.
- **`content/` stays as files under version control** until there is a
  writer who is not a committer. Version control already provides review,
  history, rollback and blame; a CMS provides those worse until somebody
  outside the repository needs to write.

## 5. Authentication and roles

**Email link plus optional passkey. No passwords, and no social login.** A
password is a liability with no upside for a product that stores a list of
places; a social login hands the identity provider a list of everywhere a
reader is thinking of going.

```
visitor        no account. Can do everything except sync across devices.
member         saved places, collections, itineraries.
contributor    may propose content; nothing published without review.
operator       claimed and verified a provider listing; may edit that listing.
editor         may publish content and record fact checks.
admin          may verify claims, suspend listings, and nothing else.
```

Row-level security on `saved_item` and `itinerary`, keyed to
`current_setting('app.account_id')`. Not application-layer checks: the
first forgotten `where account_id =` is a data breach, and there is always a
first forgotten one.

**What no role may do:** change a destination's position in any ranked list.
There is no column for it, so there is no permission for it either.

## 6. Search

Three tiers, and the first one already ships:

1. **Static index** (`/api/search.json`) — every findable thing as one flat
   row, matched in the browser with accent folding. Answers every query the
   site has today, in zero requests after the first.
2. **Postgres full-text** — `tsvector` with `unaccent`, plus `pg_trgm` for
   typos, once the index outgrows a download. Ranking is BM25-ish on
   title/summary/body with a freshness term.
3. **Vector** — `pgvector`, embeddings over destination summaries and story
   bodies, for "quiet mountain destinations in October". **Only in addition
   to tier 2, never instead of it**: a vector index cannot tell you it does
   not know, and the failure mode is a confident irrelevant answer.

The interpretation is shown back to the reader in every tier — the "you are
looking for: mountains, quiet, October" panel that ships today. That is what
lets conventional search and semantic search coexist without the reader
having to guess which one they got.

## 7. AI architecture

```
reader's sentence
   │
   ├─ (1) intent extraction    model, strict JSON out, NO FACTS
   │                            → { days, budget, month, interests[], geo[] }
   ├─ (2) retrieval            SQL and the search index, over OUR data only
   ├─ (3) planning             lib/engine, deterministic, no model
   ├─ (4) narration            model, given ONLY step 2's rows
   └─ (5) refusal              a check, not a prompt
```

The load-bearing decisions:

- **The model never plans.** It reads the sentence and it writes the prose.
  The route, the costs and the distances come from `lib/engine`, which is
  deterministic and testable. A model that plans is a model that invents a
  town.
- **Narration is given rows, not the question.** It cannot answer from
  memory because it is not asked one.
- **Refusal is code.** `whyUnreliable()` already ships in the browser: four
  conditions under which the planner declines rather than returning a
  confident bad answer. A prompt that says "do not make things up" is a
  request; a check is a guarantee.
- **Volatile fields are refused at the schema level**, so no prompt can leak
  an opening time we do not hold — there is no column.
- **The consumer-facing name is EuropeDoor Guide.** Never "our AI". It says
  "as an AI language model" never; it speaks like somebody who knows Europe.

## 8. Seed data

The seed is this repository. `content/` is every country, region,
destination, place, experience, journey and story currently written —
validated, cross-linked, and written rather than imported. The live counts
are in `docs/content-report.md`, which is regenerated on every build; they are
not copied here, because a number copied out of a generated document is a
number that will be wrong within a month.

```
content/
  taxonomy.json          interests, months, budgets, blocs, currencies, categories
  countries/<slug>.json  country → regions → destinations → places, experiences
  journeys.json  stories.json  themes.json  fund.json  providers.json
  images.json            the photograph register
  strings/<lang>.json    interface catalogues
```

Load order: taxonomy → countries → regions → destinations → places →
experiences → providers → journeys → themes → stories → images. Every step is
idempotent on slug, so a re-seed is a re-run.

**There is no importer in this repository on purpose.** 319 destinations
written properly beats 40,000 imported, and the import is the easy half — it
is the writing that is the asset, and it is the writing that a competitor
cannot copy in a weekend.

## The trigger

Do not build any of this until one of these is true:

| trigger | what it unblocks |
|---|---|
| **An entity exists** and can be a data controller | accounts, and everything downstream of them |
| **Somebody who is not a committer needs to write** | the CMS, contributor and operator roles |
| **A business claims a listing** | operator auth, verification, the directory product |
| **The search index outgrows a download** (~2 MB) | Postgres full-text |
| **Money moves** | payments, and a great deal of compliance |

Not one of those is true today. Until one is, the correct architecture is the
one that is running: static files, no database, no server, and 988 pages that
cannot break in a way nobody notices.

The first trigger to fire will be the entity, and it is the same blocker
behind every DEFERRED row in `docs/section-audit.md`. That is worth saying
plainly: **the bottleneck is not technical, and no amount of this document
moves it.**
